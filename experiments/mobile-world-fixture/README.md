# Общий мир: минимальный Lua-ресурс

Это источник будущего E2E-проверочного ресурса MTA. Он ещё не доказывает работу
собственного транспорта, Android, Lua runtime или общего мира. Синтаксическая
проверка файлов тоже не заменяет выполнение в MTA.

## Запуск в изолированном стенде

1. Скопировать эту папку в `resources/mobile-world-fixture` тестового сервера.
2. Подключить два клиента с одинаковой экспериментальной версией протокола.
3. В серверной консоли выполнить `start mobile-world-fixture`, затем
   `mobilefixture create`. Для команды игрока требуется явное ACL-право
   `command.mobilefixture`; право не выдаётся этим ресурсом. Консоль разрешена.
4. Включить клиентский `debugscript 3`; сохранить server log и client debug logs
   с указанием platform, build commit, transport, session и имени игрока.
5. Подойти к координатам `1480, -1730, 13.6` в dimension/interior 0.
   Ресурс не телепортирует игрока и не меняет его игровые настройки.
6. Повторить `mobilefixture create`: ожидается `already_active`, вторая машина
   не создаётся. `mobilefixture cleanup` удаляет активную машину.

`mobilefixture status` печатает текущее состояние. Ресурс использует только
стандартный автомобиль 411 и небольшой `http-witness.txt`. Не запускать в production RP.

`client.lua` имеет `cache=false` и передаётся пакетами MTA. Отдельный `<file>`
нужен для G4 HTTP download: запускать с пустым изолированным cache, сохранить
реальный HTTP request/response и hash файла. Клиент пишет `http_asset_read` после
fileOpen/read/close и проверки содержимого; при ошибке не посылает ready.
Одна эта запись без HTTP evidence не доказывает скачивание. Серверный Lua не менялся.

Перед запуском сгенерировать manifest из фактических байтов checkout:
`python content_manifest.py --http-base http://127.0.0.1:22005`.
`--destination-prefix` должен совпадать с путём ресурса относительно отдельного
client cache root. Генератор описывает только `<file>` entries, не packet-delivered
client.lua. JSON с URL/raw SHA256/size — вход явной lab policy, не evidence скачивания.

## Что именно сравнивать

`mobilefixture:correlation` — диагностический ID, сформированный сервером для
одного создания. Это **не внутренний MTA ElementID**, не GTA pool handle и не
указатель. Внутренние идентификаторы клиентских GTA могут различаться.
Один correlation должен относиться к одному серверному vehicle и его воплощению
на каждом клиенте. После restart ресурса создаётся новый correlation.

Сервер инициирует `probe` с токеном и ссылкой на vehicle. Клиент проверяет
correlation, пишет модель/позицию/streaming и возвращает ссылку и токен. Сервер
проверяет `client == source`, ожидаемый токен, срок 10 секунд и тот же element.
ACK доказывает доставку события и корректное отображение element reference
в Lua. Он не доказывает честность клиента, физику, графическое появление машины
или работу античита. Изменение клиентом element data не считается авторитетным
источником: сервер сопоставляет ответ со своим локальным correlation.

## Условия PC → PC, затем PC → Android

- В серверном логе один `created`, в каждом клиентском — `probe_received` с тем
  же correlation и моделью 411; сервер получает `probe_ack` от обоих игроков.
- Оба игрока действительно видят одну машину. Приложить независимые снимки или
  запись; одних логов для этого утверждения недостаточно.
- Водитель и пассажир одновременно находятся в машине; оба клиента видят
  движение и смену водителя. Допустимые сетевые погрешности и интервал
  наблюдения задать в плане транспорта до измерения.
- Поздно подключившийся клиент получает активную машину и probe после запуска
  клиентского ресурса. Выход и повторный вход не создают дубликат.
- Уход из streaming range и возвращение дают `stream_out`/`stream_in`; correlation
  сохраняется. Это проверяется после прихода element data, которое может быть
  отдельным событием.
- Выполнить 10 циклов create/повторный create/cleanup и 3 restart ресурса.
  После cleanup и stop нет fixture vehicle; после restart нужен новый create.
- Проверить запрет команды без ACL и отсутствие ACK для события с чужим source,
  неизвестным/просроченным токеном или иной ссылкой на элемент. Ресурс игнорирует
  такие ответы; это не полноценный security audit.

Headless-сервер с одним сетевым echo-клиентом не выполняет эти критерии.
Сохранять результат каждой стадии как `not_run`, `passed` или `failed` вместе с
логами и build IDs. Для Android отдельно записать ABI, API level, device/AVD и
build fingerprint игровых библиотек. PC-результат не засчитывать за Android.

## Статическая проверка

Из корня репозитория: `python experiments/mobile-world-fixture/validate.py`.
Проверяются XML и существование безопасных относительных script paths.
Если доступен `luac` Lua 5.1: `luac -p server.lua client.lua` из этой папки.
Ни XML validator, ни `luac` не исполняют ресурс в MTA.
